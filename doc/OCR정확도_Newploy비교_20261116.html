스캔 PDF 글자 정확도 비교 — 우리 OCR vs Newploy

같은 스캔 PDF 38쪽을 우리 OCR(models/ocr: PP-OCRv6 tiny 검출 + 한국어 PP-OCRv5 mobile 인식)과 Newploy AI Desktop OCR(PP-DocLayout 레이아웃 + PP-OCRv5 server 검출 + 자체 학습 CTC 인식기)에 넣고, 원래 PDF 의 텍스트층을 정답 삼아 글자를 채점했다. 결론부터 말하면 전체 점수는 우리가 높고, Newploy 가 진 이유는 대부분 '잘못 읽어서'가 아니라 '안 읽고 빠뜨려서'다.

쪽을 고른 기준

  • 공백 뺀 글자 150~2,500자, 한글 비율 50% 초과, 깨진 글자(U+FFFD) 없음
  • 그림 면적이 쪽의 20% 미만 — 그림 속 글자는 텍스트층(정답)에 없기 때문
  • 쓸 만한 쪽이 3쪽 이상인 문서에서 최대 5쪽을 무작위로

Newploy 를 돌린 방법

앱을 --remote-debugging-port=9333 으로 띄우고, 화면에서 끌어다 놓기를 할 때 앱이 부르는 것과 같은 window.newploy.library.addPaths(폴더id, 경로들) 로 'OCR비교' 폴더에 8개를 넣었다. 앱이 스스로 '텍스트층 없음 → OCR' 경로를 골라 처리했고, 결과는 %LOCALAPPDATA%\Newploy\AI Desktop\work\<id>\result\document_result.json 의 영역별 text (표는 내보낸 HTML·TSV)를 이어 붙여 썼다. 암호화된 모델을 앱 밖에서 따로 돌리지 않았다.

지표 읽는 법

지표뜻
글자 F1공백을 뺀 글자를 개수로 맞춰 본 점수. 읽는 순서와 상관없다 — 정답 텍스트층과 OCR 의 줄 순서가 달라도 공정하다. 이 보고서의 기준 지표.
글자 재현율정답 글자 중 OCR 이 내놓은 비율. 낮으면 '빠뜨림'.
글자 정밀도OCR 이 내놓은 글자 중 정답에 있는 비율. 낮으면 '틀리게 읽음' 또는 '정답에 없는 글자(그림 속 글자 등)를 더 읽음'.
한글 F1 · 영문·숫자 F1그 글자만 남기고 잰 글자 F1.
단어 재현율정답의 2글자 이상 단어가 OCR 결과에 그대로 들어 있는 비율 — 검색에서 '그 단어로 찾아지는가'에 가깝다.
띄어쓰기 F1공백이 들어간 자리가 정답과 겹치는 정도.
CER편집 거리 ÷ 정답 글자 수. 읽는 순서까지 따져서 순서가 다르면 크게 나빠진다 — 참고만 한다.

여러 쪽을 묶을 때는 정답 글자 수로 가중 평균했다(짧은 쪽이 점수를 흔들지 않게).

07우리 정밀도가 낮은 이유

우리 글자 정밀도(0.838)가 낮은 것은 대부분 정답에 없는 글자를 더 읽었기 때문이다. 우리는 쪽 전체에서 글자 줄을 찾으므로 도식·화면 캡처 안의 영문·숫자까지 읽는데, 이 글자는 원래 PDF 에서도 그림이라 텍스트층(정답)에 없다.

  • 출력 글자 ÷ 정답 글자: 우리 1.17 · Newploy 0.74 (표 오류 쪽은 우리 1.26)
  • scan03 1쪽(우리 0.676 · Newploy 0.980): 우리가 더 읽은 글자는 도식 속 영문(ABCDMMMMPPPRRSSS…aaaa…)
  • scan06 2쪽(우리 0.701 · Newploy 0.896): 화면 캡처 속 콘솔 숫자·기호(###()----///000…111…)
  • 한글만 보면 우리 정밀도도 0.976 — 남는 글자는 주로 영문·숫자다
검색용으로는 그림 속 글자를 읽는 쪽이 득일 수 있다. 다만 정답이 없어 이 글자들이 맞게 읽혔는지는 이번 측정으로 알 수 없다.

11주의할 점 (측정 한계)

  • 진짜 스캔본이 아니다. 깨끗한 PDF 를 200dpi 로 렌더한 그림이라 기울어짐·번짐·얼룩이 없다. 실제 스캔본에서는 두 쪽 모두 점수가 더 낮을 것이고, 레이아웃·기울기 보정이 있는 Newploy 가 유리할 수 있다.
  • Newploy 표 단계 오류는 이 PC 설치판의 문제일 수 있다. 표 쪽 결과는 Newploy 의 실력이 아니라 설치 상태를 잰 것일 수 있다.
  • 정답에 그림 속 글자가 없다. 그래서 그림 속 글자를 읽는 우리 쪽 정밀도가 실제보다 낮게 나온다. 반대로 Newploy 가 그림을 건너뛰어도 손해가 정답 범위 안에서만 잡힌다.
  • 38쪽 · 8문서는 작은 표본이다. 본문만 있는 쪽의 차이(0.962 vs 0.935)는 작아서 쪽을 늘리면 바뀔 수 있다.
  • Newploy 맞춤법·LLM 보정 단계가 이번 결과에 들어갔는지는 확인하지 않았다(결과 파일의 최종 글자를 그대로 썼다).
  • 둘 다 CPU 로 돌렸다. GPU 가 있으면 Newploy(PyTorch) 속도가 크게 달라질 수 있다.

12다시 돌리는 법

스크립트는 tools/ocr_compare/, 시험셋·결과는 tests/private/ocr_compare_newploy/(실제 문서라 git 제외)에 있다.

파일내용
tools/ocr_compare/make_set.py원본 폴더 → set/scanNN.pdf + set/truth.json(정답·원본 경로·쪽 번호)
tools/ocr_compare/run_ours.pysdp.exe parse → ours/scanNN.json
tools/ocr_compare/newploy.pyadd 앱에 넣기 · status 진행 · fetch 결과를 newploy/ 로 복사
tools/ocr_compare/evaluate.py채점 → scores.json(쪽별) · summary.json(묶음·문서별)
# 1) 시험셋 (이미 있으면 건너뜀 · pymupdf 필요)
python tools/ocr_compare/make_set.py "D:\분류함" 8
# 2) 우리 OCR
python tools/ocr_compare/run_ours.py
# 3) Newploy — 앱을 디버그 포트로 띄운 뒤 (playwright 필요)
& "$env:LOCALAPPDATA\Programs\Newploy AI Desktop\Newploy AI Desktop.exe" --remote-debugging-port=9333
python tools/ocr_compare/newploy.py add
python tools/ocr_compare/newploy.py status   # 모두 completed* 가 될 때까지
python tools/ocr_compare/newploy.py fetch
# 4) 채점 (rapidfuzz 필요)
python tools/ocr_compare/evaluate.py

모델을 바꾼 뒤에는 2)와 4)만 다시 돌리면 같은 Newploy 결과와 비교할 수 있다.
