OCR 속도 개선 설계서 — 아레나 켬 + 실행마다 줄이기 · 큰 쪽 · 큰 그림 A4 상한

스캔 쪽 OCR 이 글 많은 쪽에서 7~8초 걸리는 것을 줄인다. 실측(2026-11-16 ~ 17)으로 고른 두 가지를 함께 적용한다. ① OCR 세션의 메모리 아레나를 켜고 실행이 끝날 때마다 줄인다 — 인식이 빨라진다. ② A4 보다 큰 PDF 쪽과 그림 파일은 A4 크기로 줄인다 — 큰 쪽의 검출 시간과 메모리 최대치가 준다. 코드는 문서 파서 저장소 Struct-DocParse-OCR-rust 에서 바꾸고, SimpleRAG 는 설정을 넘기기만 한다.

1. 요약

왜 느린가쪽당 시간의 대부분은 인식이고 글자 상자 수에 비례한다(상자당 약 35ms). 글 많은 쪽(142상자)은 인식 6.8초 · 합계 7.4초. 검출은 쪽마다 0.4~0.7초로 비슷하다.
① 아레나 켬 + 줄이기335쪽 연속 처리에서 쪽당 4.02→2.68초(−33%). 쥔 메모리는 쌓이지 않음(134~325MB). 대가: 평소 +약 180MB, 순간 최대 1.3~1.5GB.
② 큰 쪽 · 큰 그림 A4 상한A4 보다 5% 넘게 큰 PDF 쪽을 A4 크기로 그린다. 그림 파일도 같은 규칙으로 줄일 수 있지만 4K 화면 캡처가 나빠져 기본은 끔(8-R). 정답 비교 글자 F1 −0.0015, 큰 쪽 검출 −45%, 그 쪽 메모리 최대치 −650MB. A4 이하는 바뀌지 않는다.
결과 · 색인A4 이하 쪽의 OCR 결과는 지금과 같다(아레나는 결과를 바꾸지 않음 — 글자 F1 1.0). 옛 OCR 캐시 · 색인은 그대로 쓴다(다시 OCR · 재인덱싱 없음).

3. ① 아레나 켬 + 실행마다 줄이기

3-1. 무엇을 하나

  • 아레나: ONNX Runtime 이 계산 중 임시 메모리를 운영체제에 매번 받고 돌려주지 않고, 자기 창고(아레나)에 받아 두고 나눠 쓰는 방식. 한 번 계산(실행)에 수백 번 있는 임시 메모리 요청이 운영체제를 거치지 않아 빠르다.
  • 실행마다 줄이기: 실행(run 한 번 — 검출은 쪽당 1번, 인식은 상자 6개마다 1번)이 끝날 때 아레나의 안 쓰는 부분을 운영체제에 돌려준다. ONNX Runtime 실행 옵션 memory.enable_memory_arena_shrinkage = "cpu:0".

3-2. 바꿀 곳

  1. session.rs make_session_lean(path, threads) → 아레나를 옵션으로: with_arena_allocator(cfg().ocr_arena). 함수 이름 · 주석도 맞춘다(지금 "아레나 끔" 이 이름에 박혀 있음).
  2. ocr/det.rs · ocr/rec.rs 의 sess.run(feeds) → sess.run_with_options(feeds, &run_opts). run_opts 는 아레나가 켜져 있을 때만 줄이기 항목을 넣는다(꺼져 있으면 빈 옵션 = 지금과 같음). 실행마다 새로 만들지 말고 엔진(Engine)에 하나 만들어 둔다.
  3. 측정 때와 같은 방식이다(측정 폴더의 det.rs · rec.rs 수정과 같은 내용).
OCR 결과는 바뀌지 않는다 — 아레나는 메모리 받는 방법만 바꾼다. 측정에서 아레나 끔 · 켬 · 켬+줄이기의 글이 모두 같았다(글자 F1 1.0000).

4. ② 큰 쪽 · 큰 그림 A4 상한

4-1. 규칙

  • PDF 쪽을 200dpi 로 그렸을 때 크기가 긴 변 2,339 · 짧은 변 1,654 픽셀(A4 를 200dpi 로 그린 크기)을 넘으면, 두 변이 이 안에 들어오게 해상도를 낮춰 그린다. dpi = 200 × min(1, 2339 / 긴 변, 1654 / 짧은 변)
  • A4 이하 쪽은 지금과 똑같다(200dpi). 가로 쪽도 같은 규칙(긴 변 · 짧은 변 기준).
  • 5% 여유 구현 중 추가 2026-11-17 — 배율이 0.95 이상(A4 보다 5% 이내로 큼)이면 줄이지 않는다. 실제 문서 84건 비교에서 pt 반올림 때문에 A4 를 1픽셀 넘는 쪽(1655×2339)이 0.9997배로 줄어 결과가 달라졌다. US Letter(1700×2200 → 0.97배)도 그대로 둔다.
  • 그림 파일(png · jpg · tif · bmp)에도 같은 상한을 둔다 2026-11-17 결정 — 그림이 긴 변 2,339 · 짧은 변 1,654 픽셀을 넘으면 같은 비율로 줄인다. 그보다 작은 그림(대부분의 화면 캡처 1920×1080 등)은 지금과 같다.
    • PDF 와 달리 다시 그릴 수 없으므로 그림 픽셀을 줄인다. 많이 줄일 때(0.5배 등) 글자가 깨지지 않게 단순 선형 보간이 아니라 넓이 평균(area) 줄이기를 쓴다.
    • 검출과 인식을 모두 줄인 그림으로 한다. 검출만 줄이고 인식은 원본에서 잘라내는 방식은 실측에서 글자 F1 이 0.81 로 떨어졌다(2026-11-16, 검출 0.75배).
    • 지금 있는 ocr_image 의 긴 변 4,000 상한(RapidOCR 값)은 그대로 둔다 — 새 상한이 더 작으므로 사실상 새 상한이 먼저 걸린다.
    • 측정하지 않은 부분이 있다: 고해상도 화면 캡처(4K 3840×2160 → 0.61배로 줄어 12픽셀 글자가 약 7픽셀)와 휴대폰 사진(4032×3024)의 작은 글자. 8-3 에서 재고, 떨어지면 그림 파일 상한 규칙을 바꾼다(9장).

4-2. 바꿀 곳

  1. pdfium.rs render_page(data, index, dpi) 에 상한을 받는 판을 더한다: render_page_capped(data, index, dpi, cap) → 쪽 크기(pt)를 먼저 읽어 실제 해상도를 정하고, 그린 그림과 실제 해상도를 함께 돌려준다(Rendered.dpi).
  2. ocr/run.rs(대기열 OCR) · api.rs ocr_file(시험 명령)이 이것을 쓴다.
  3. 좌표를 200dpi 기준으로 되돌려 저장: OCR 줄 상자는 실제 해상도 그림의 좌표이므로, 글자층 겹침 빼기(drop_overlapping — 같은 해상도 좌표끼리 비교)를 한 뒤 × 200 / 실제 dpi 로 늘려 캐시에 넣는다(5장).
  4. 그림 파일: ocr/run.rs 의 그림 경로(쪽 그림을 읽은 뒤)와 api.rs ocr_file 에서 상한을 넘는 그림을 imgops 의 새 넓이 평균 줄이기로 줄여 OCR 하고, 상자 좌표는 ÷ 줄인 배율 로 원래 그림 픽셀 좌표로 되돌려 캐시에 넣는다(그림 파일 캐시는 지금도 원래 픽셀 좌표, dpi: 0). 아이콘 거르기(짧은 변 100 미만)는 줄이기 전 크기로 판단한다.

8. 확인 방법

  1. 결과가 그대로인지 — A4 이하 문서: 시험 문서 10건(tests/samples) · 실제 문서 84건 블록 JSON 이 고치기 전과 글자 하나까지 같아야 한다(sdp.exe dump → compare). 리눅스도 같은 비교(scripts/linux-build.sh).
  2. 큰 쪽 정확도 — 2-3 의 글자층 40쪽 1.33배 · 1.41배 시험을 실제 코드로 다시: F1 이 0.892 이상.
  3. 그림 파일 정확도 (새로 잼) — 상한 전 · 후 글을 비교한다.
    • 스캐너 흉내: 글자층 40쪽을 300dpi(2480×3508) · 600dpi 그림 파일로 만들어 OCR — 글자층이 정답. F1 이 원래 크기와 0.005 넘게 차이 나지 않아야 한다.
    • 고해상도 화면 캡처: 4K(3840×2160) · QHD(2560×1440) 화면 캡처 20장(작은 메뉴 글자 포함) — 정답이 없으므로 상한 전 · 후 글 일치와 줄 수를 본다.
    • 휴대폰 사진(4032×3024) 10장 — 같은 방식.
    • 떨어지면: 그림 파일은 상한을 끄거나(ocr.image_cap=false), "글자 높이가 일정 픽셀 이하로 작아지지 않는 만큼만 줄이기"처럼 규칙을 바꾼다.
  4. 캐시 좌표 · 구조 분석 — 큰 쪽 문서(KISA)를 상한으로 OCR 한 뒤 캐시 좌표의 최대값이 그 쪽의 200dpi 크기 안에 있고, 구조 분석 블록이 옛 방식과 같은 모양(다단 · 머리말 판정)인지.
  5. 속도 · 메모리 — 335쪽 연속 처리(2-2 와 같은 4문서)를 실제 DLL 로: 쪽당 시간 −25% 이상, 쥔 메모리가 300쪽 넘게 돌아도 늘지 않음(350MB 안).
  6. 앱 — 설치본에서 스캔 문서 폴더(D:\샘플문서\scanpdf)를 새로 색인해 OCR 대기열이 끝까지 돌고, 워커 메모리(작업 관리자)가 OCR 중 · 끝난 뒤 얼마인지 기록.
  7. 옵션 — ocr.arena=false · ocr.page_cap="none" 이면 지금(0.1.0)과 결과 · 메모리가 같다.

10. 정할 것

10-1. 스레드 수 — 4 그대로 / 8측정에서 아레나 켬 + 줄이기 + 8스레드가 4스레드보다 조금 빨랐다(글 적은 쪽 인식 364→241ms). 하지만 2026-11-13 측정은 "8 이 4 보다 느림"이었고 부하에 따라 흔들린다. 제안: 4 그대로 이번에는 두 가지만 바꾸고, 스레드는 앱 측정(8-5) 뒤 따로 본다.
10-2. 그림 파일에도 상한을 둘까정함(2026-11-17): 구현은 넣고 기본은 끔 4-1 · 4-2 대로 넓이 평균으로 줄이는 코드는 넣었다(ocr.image_cap=true 로 켬). 구현 뒤 8-3 측정에서 4K 화면 캡처 F1 이 0.958 → 0.913 으로 떨어져, 사용자 결정으로 기본은 끈다(8-R). 스캐너 그림 · 사진은 괜찮았다.
10-3. 옛 OCR 캐시를 다시 읽을까(엔진 이름 올림)제안: 올리지 않음 큰 쪽의 두 방식 결과가 99% 이상 같고, 다시 읽으면 운영 스캔 약 3,000쪽을 2~3시간 다시 OCR 한다. 새로 들어오는 큰 쪽만 상한으로 읽는다.
10-4. 실행마다 줄이기 / 쪽마다 한 번 줄이기제안: 실행마다 측정한 방식이다. 쪽 끝에 한 번만 줄이면 조금 더 빠를 수 있지만 재 보지 않았다. 필요하면 구현 후 같은 335쪽으로 비교한다.
